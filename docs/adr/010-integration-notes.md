# ADR 010: Integration notes: wiring the Super-agent milestones together

Status: accepted (integration of milestones 1-7 and 9 of the Super-agent architecture)

## Context

Milestones 1-7 and 9 (ADRs 001-007, 009) were built on separate branches and merged one after another. Each one was tested on its own, with its neighbours mostly off, so the places where two of them meet were wired only as far as the second branch happened to know about the first. Reading the merged code against the design notes turned up these gaps:

- A background job's result (ADR 004) was a Trigger on the chat's thread only. Chat threads cannot be subscribed (ADR 003), so a test run or a build in a folder that Workers share never reached them, which defeats the point of shared threads ("shared environments surface conflicts through shared Threads").
- Recall (ADR 005) knew `job_…` ids, but only inside the chat that ran the job. The Watchdog's ids (ADR 006) were not recallable at all, even though a Watchdog notice reaches a Router as an environment event whose id is the action's (`wa_…`): the Router's batch named an id that `recall` could not resolve.
- The Watchdog read the friction log, but not the lifecycle audit log (ADR 007), so an agent the command guard refused again and again was invisible to the one component whose job is noticing agents that loop or drift.
- The `<untrusted>` wrapper (ADR 007) covered page text, console output and event payloads, but background job output, recalled environment objects and the Watchdog's snapshot kept fences of their own (`<job_output>`, a note line, defused text), and the Watchdog's system prompt did not carry the rule the other prompts carry.
- The Watchdog's session (and the Router's) had no deny hook. Both have no built-in tools, so nothing could reach the guard today; the hard rules still held for chat bots, Workers and jobs only by construction, not by the same code path.
- Per-role model routing (ADR 009) had an end-to-end test for the Watchdog and for bots, not for the Router and its Workers.
- Nothing checked, across all milestones at once, that with every new setting off Crew starts no new process, writes no new file and makes no model call it did not make before.

## Decision

Wire each seam in code, test it end to end, and keep every addition behind the switches that already exist: no new setting.

## What did not change

- No new setting, no migration. `job` stays a source without settings (`FilteredSource` excludes it); its workspace copy only ever goes to subscribers.
- The explicit job result, its turn for the bot that started it, mid-turn injection and the chat's notice are exactly as in ADR 004.
- The Watchdog still cannot start work, approve anything or apply a change; its new input (the audit log) only adds flags and lines to its snapshot, and the audit log stays opt-in.
- Workers still never get the full-duplex tools (ADR 004): they receive job results from others; they do not start jobs.

## Deferred

- **Speculative execution (milestone 8)** is not built: no silent reproduce-and-fix Workers, no `skills.forFamily(…, 'speculative')` caller, and the gateway's `speculative` role and spend windows have no sessions using them yet. (Since built on top of this integration: [ADR 008](008-speculative.md).)
- **Guard refusals with the audit log off.** The Watchdog sees refusals only while `safety.audit` is on, since that log is opt-in (it writes commands to disk). Recording refusals in the always-on friction log would change what Crew writes with default settings; left for a decision.
- **Credential brokering** (letting an agent use a token it cannot read, as yetone/magpie's gateway can): still only stripping and masking (ADR 007, ADR 009).
- **Job results across projects.** A job's environment Trigger goes to the workspace thread of the exact folder it ran in. A job in a chat's own git workspace reaches only Workers of that chat (they subscribe to the chat's workspace thread); a job in the project's main folder does not reach Workers working in a chat workspace branched from it. Mapping "same files" across worktrees is left out.
- **The Watchdog's view of background jobs.** It can `inspect` a `job_…` id it meets, but its snapshot does not list long-running or failed jobs: they belong to chat bots, which it never steers (ADR 006).
- **Playwright e2e tests** of the Workers bar, the Background jobs bar and the Triggers view: the integration tests drive the same APIs and events offline; a browser test was not added.
- **Recall from the Watchdog.** The Watchdog keeps `inspect`, which reads any id without a chat scope; it does not get `recall`, whose scope is a chat.

## Risks

- **More events into a Worker's context.** A busy shared folder with a full-duplex bot running many jobs could push many job results to its Workers. Bounds: only active subscribers get one, the inbox keeps 20, and each is about 60 words with the rest behind recall; a Worker can `unsubscribe_thread` or `hand_back`.
- **Prompt injection through job output into another chat's Worker.** The output is someone else's program's output now reaching a Worker that did not ask for it. It arrives as an environment event in the `<untrusted>` wrapper, cannot start work (only active Workers receive it), and the Worker's prompt says to act only if it bears on its task.
- **A wider recall scope.** A job is now recallable from a chat other than its own, but only one whose Workers were handed its result; the output they could recall is the output they were already sent the end of.
- **Behaviour drift when off.** Every addition sits behind a switch that already existed (`superAgent.enabled` with direct routing, the chain of recall, the Watchdog, the audit log); the format changes (the `<untrusted>` wrapper on job output) apply only to full-duplex bots, which are off by default. `super-agent-off.test.ts` pins the rest.

# ADR 110: Finishing what the Super-agent integration deferred

Status: accepted (on top of `superagent-polish`: ADRs 011 and 106-109)

## Context

The integrated, polished Super-agent mode left a list of items for later (ADR 011 "Deferred", ADR 107 "Left for later"), and GitHub Actions was red on every Super-agent branch: "Typecheck, lint, unit and integration tests" failed on `ubuntu-latest` with 17-19 failing tests (injection, wave2-seams, full-duplex, super-agent-flow, speculative, seams, subscriptions, claude-cli, gateway), 120 s timeouts, and finally `JavaScript heap out of memory`, while the suite passed on a developer machine. This ADR covers, in order: making CI green (0), speculative fixes on pull requests (1), recall of speculative runs (2), and browser tests for the background bars and meters (3).

## 0. CI on `ubuntu-latest`

Three independent causes, each found from the CI logs and reproduced locally.

| Cause | What happened | Fix | Where |
| --- | --- | --- | --- |
| **The sandbox could not start, but Crew said it could.** | Ubuntu 24.04 restricts unprivileged user namespaces with AppArmor. `bwrap --unshare-all true` (Crew's probe) succeeds, but Claude Code's sandbox also sets up a user namespace *nested* inside bubblewrap's (its seccomp helper writes `/proc/self/setgroups`), and AppArmor strips the capabilities that needs. Every sandboxed command failed with `apply-seccomp: … Permission denied`. Mock-model scripts that wait for a tool result containing a marker then re-issued the same call forever: turns ran into the 120 s timeout, and the mock provider kept every request body (each about 100 kB with Claude Code's system prompt and tools) until the test worker's heap ran out. A test written for this ADR reproduced the same OOM when its marker did not match. | Crew's probe now also runs a nested `unshare --user --map-root-user` inside bubblewrap and reports the sandbox **unavailable**, with a hint naming the sysctl, where it fails (`probeSandbox`, pure apart from its exec, unit-tested). On a user's machine that means commands run unconfined with the deny list and the gate, and Settings says why, instead of every command failing. CI lifts the restriction (`kernel.apparmor_restrict_unprivileged_userns=0`, and unloads a bwrap AppArmor profile if one is loaded) and then **asserts** that the nested namespace works, so the tests that need the sandbox run on CI instead of being skipped. | `server/sandbox.ts`, `scripts/ci-sandbox.sh`, `.github/workflows/ci.yml`, `tests/unit/sandbox.test.ts` |
| **Model gateway streams hung on Node 24.** | The gateway reads a stream's first event, pauses the upstream response, and then waits for `'end'` with a new listener. When the whole answer arrives in one chunk, Node 24 emits `'end'` while the stream is paused, before that listener exists, so the gateway never ends its response. Every real Claude Code turn through the gateway hung (`gateway`, `seams`' per-role routing, `super-agent-flow`'s quota hand-over, `speculative`'s gateway role). CI runs Node 24 (`.nvmrc`), and the developer machines that ran the suite had Node 22: the same tests time out locally under `/opt/node24` and pass under Node 22. | Resolve at once when the response has already ended, and on `'close'`. A unit test streams a whole answer in one write; it fails without the fix on Node 24. | `server/gateway/proxy.ts`, `tests/unit/gateway.test.ts` |
| **Too many test workers for the runner.** | Three files per CPU (12 on a 4-CPU runner), each with a server and sometimes several Claude Code processes. | Two per CPU and at most one per 1.5 GB: 8 on a 4-CPU, 16 GB runner. | `vitest.config.ts`, `CONTRIBUTING.md` |

`subscriptions`' "rule candidate instead of subscribed" and `full-duplex`'s failed job were the sandbox too: a Worker's `sleep 2` failed at once, so it finished before reading the event, which went back to the filter; the background `sleep 2; echo mock-build-ok` ran as a sandboxed Bash call and failed.

### `tests/integration/sandbox.test.ts` fails wherever the sandbox works

Not changed, as instructed, and **still failing** (3 of its 4 tests) on CI and on any machine where the sandbox starts. It is not the environment. Its first case runs `curl` to a LAN address that is not allowed and expects the *sandbox's* denial (`deny network-outbound … host is not on the allow list`). Since milestone 7, Crew's command guard refuses that `curl` first, at PreToolUse, with its own message, which does not echo the command's `sb-1` marker. So the test's mock script never sees its first step finish, re-issues it until the 120 s timeout, and its later cases then read results from that looping session. The test was written before the guard. It skipped everywhere bubblewrap was missing and failed for the seccomp reason on CI, so nobody saw the conflict. A scratch probe (not committed) showed the sandbox itself does what the test means: with Crew's settings, an allowed LAN address and this machine are reached, and others are blocked. Making it pass needs a decision this ADR does not take. Either the test accepts the guard's refusal as the block (it would then fail only when neither layer blocks), or the guard leaves network decisions to the sandbox while the sandbox is on (that removes a layer ADR 104 keeps on purpose). Until then CI shows these 3 failures; every other test passes there.

## 1. Speculative fixes on pull requests

- **Fetching the head.** When a failing GitHub check's head commit is not local, `decide` looks for a local remote that reaches the pull request's repository (`speculative/pr.ts` `remoteFor`: the URL's last two path segments, any host, `origin` first). With one, the gate lets the run start (`GateInput.head.fetchFrom`) and the run records `Speculation.github.fetch = { remote, ref: refs/pull/<n>/head }`. Before its worktree is made, the run fetches that ref (`SpeculativeHost.fetchBase`): `git fetch --no-tags --no-write-fetch-head --no-recurse-submodules <remote> refs/pull/<n>/head`, with the user's environment (their credentials reach the remote; it only reads), hooks off and no terminal prompt. Only objects are added: no branch, tag or `FETCH_HEAD` of the user's changes. It is refused when the repository's own config sets a key that runs a program or redirects git (`riskyConfigKeys`, as for drafts): this runs unattended, and an agent may have planted such a key. If the ref no longer points at the commit the check failed on, the run is discarded ("The pull request moved on"). With no remote for the repository it is skipped with the old reason.
- **Pushing back, as a draft.** When a run for a pull request is verified, Crew reads the pull request (`gh api repos/<repo>/pulls/<n>`, a GET) and decides with `pushPlan` (pure): the pull request's own branch, through the local remote that reaches the repository the branch lives in. The result is a `git-push` draft (milestone 7) that runs from the fix's worktree, whose `HEAD` is the fix committed on the pull request's head, so the push is a fast-forward. The card shows the exact command (`git push <remote> HEAD:refs/heads/<branch>`), the remote and its URL, and the branch, and the Speculative fixes bar says the same. Nothing is pushed until the user approves the draft, which then re-checks the push URL and the repository's config like any push draft. It is **not offered**, with the reason kept in `Speculation.github.push.refused` and shown on the card, for a closed pull request, a source repository that was deleted, a fork the user cannot push to (GitHub's `permissions.push` on the fork is not true, and it is not a fork open to maintainers whose base the user can push to), a base the user cannot push to, or when no local remote reaches the branch's repository. Discarding the fix discards the push draft with the comment draft. Merging the fix locally withdraws the push, since its worktree goes away.
- **No new setting, no migration.** `Speculation.github.fetch` and `.push` are optional (`SpeculationGithub` in `shared/types.ts`).

Tests: `tests/unit/speculative-pr.test.ts` (remote matching, the gate with a fetchable head, every `pushPlan` outcome). `tests/integration/speculative-pr.test.ts` (demo mode, a fake `gh`, a local bare repository at `<tmp>/acme/shop.git` standing in for GitHub): a head that is not local is fetched and the run is ready at it, with no user ref moved and no `FETCH_HEAD`. The push draft shows the exact command, remote URL and branch, and the branch is untouched until approval. Discarding the fix discards both drafts. Approving pushes a fast-forward and records how to undo it. A fork without push rights gets no push. Merging locally withdraws the push.

## 2. Recall of speculative runs

`sp_…` resolves like other references (`speculative/recall.ts`, registered with `registerRecall`). The scope is a run surfaced in the caller's chat, or one made for the caller's project. A blind reviewer never gets there. The node is compact, so it stays within Inline & Spill's budgets: the signal, the status, the **verdict** as Crew's checks established it (`verified: \`<check>\` fails without the fix (exit 1), passes with it (exit 0)`, or why it never ran or was discarded), the **diff stats** (files, lines added and removed, how many are the reproduction), the pull request and the push (drafted, or why not), and when. The body holds the run's summary and the file list. The summary is a model's words written after reading outside input, so the body is in the `<untrusted>` wrapper. The links lead to the signal's Trigger, the run's Worker and the surfaced Trigger. The **full diff** is a link, `sp_…/diff`, which renders `git diff base head` from the run's worktree as untrusted data, paged with `from` like any long text. Once the worktree is gone (merged or discarded), the link and the error say so. The Router's event about a ready fix now names the run (`Run: sp_… (recall it for the verdict and the diff)`), and `RECALL_TOOL` lists `sp_…`.

Tests: `tests/unit/speculative-recall.test.ts` (verdicts by status, stats, the rendered node: compact, fenced, the diff as a link only). `tests/integration/speculative-recall.test.ts`: a fix made in demo mode survives a restart. The real Claude Code, against the mock model, recalls `sp_…` from another chat on the same project and gets the compact form, then `sp_…/diff` and gets the diff as untrusted data, and an unknown id gets a plain error.

## 3. Browser tests for the bars and meters

`tests/e2e/super-agent-bars.spec.ts`, offline with the demo agent:

- The Background jobs bar lists a running job (its command, Running, Stop). The Activity page lists it with who started it and where, and one click stops it. The bar then says Stopped.
- A speculative fix appears on the Activity page while Crew runs its checks (Checking, the check command, its Trigger, Stop), then under "Waiting for you" and in the chat's Speculative fixes bar with its proof. The Watchdog page shows the speculative runs' spend today as a second meter beside its own budget. Discarding the fix empties both lists.

The test found a bug: the Watchdog page's speculative meter came from the Watchdog's own pushed state, which a speculative run never moves, so a finished run stayed "running" and its spend $0.00. The page now reloads its overview when a speculative run changes, and the meter reads the reloaded figure (`WatchdogView.tsx`).

The Workers bar and the Activity page's Worker rows were already covered (`super-agent.spec.ts`, `super-agent-ux.spec.ts`).

## Results

Local machine (4 CPUs, 16 GB, root, bubblewrap and socat installed for this work, Claude Code 2.1.317, Node 22): `npm run typecheck` and `npx biome ci .` pass. `npx vitest run` passes except `sandbox.test.ts` (3 tests, for the reason above). The new browser tests pass 6 of 6 with `--repeat-each=3`, and the existing Super-agent browser tests still pass. The gateway tests were run on Node 24 before and after the fix: 2 failed before, 10 of 10 passed after.

CI on `superagent-finish` (`ubuntu-latest`, Node 24, the newest Claude Code): before, 19 failed tests, timeouts and an out-of-memory crash (runs on `superagent-polish-tests`/`-code`). After the sandbox probe and the CI step (the nested namespace check passes on the runner), 8 failed and nothing ran out of memory: 5 tests through the gateway and 3 in `sandbox.test.ts`. After the gateway fix, `sandbox.test.ts`'s 3 are the only failures, in 316 s. Browser tests pass.

## Still left

- **`sandbox.test.ts` against the command guard** (above): a decision on which layer the test should expect.
- From ADR 011: speculation from other GitHub events; the Watchdog's view of speculative checks; sandboxed speculative checks across a crash; speculative spend in the gateway's windows; the bench's channel arm with a real model.
- **A push draft after a local merge.** Merging withdraws the push, because it ran from the throwaway worktree. Pushing from the user's folder would push whatever else is on their branch, so it is left to the user.
- **Forks the user can push to but has no remote for** get no push. Crew does not add remotes.
- **Browser tests of the Speculative fixes bar with GitHub drafts** (the comment and the push line): the integration tests drive the same data, and the e2e harness has no fake `gh` per test yet.
- From ADR 106 and 107: a "chain is over" signal for the `stall` and `auto-challenge` helpers, the unlabelled controls outside the Super-agent views, and the sidebar's truncated labels.
- The mock provider keeps every request. A script that loops fills the heap before the test times out; a cap that fails the test with a clear message would turn the next such loop into a readable failure.

## [Unreleased]

### Added

- **Super-agent: channel norms** (per-channel output; in Router mode, no new setting except the optional webhook). Router replies stay within the chat profile: at most 100 words and 6 lines, marked as a decision, a question or a request to accept work, and never code, logs, diffs or other tool output (refused in code, so the Router rewrites them). The Workers' full reports sit under a collapsed Details row below the reply that sums them up, kept even after a Worker is dismissed. Pull requests, issues and release notes that agents draft are checked for structure and long output is folded. A project can send the Router's questions and acceptance requests to a Slack or Feishu webhook: off by default, enabled only by you, only the kinds you pick, only the reply's words; the URL stays in `~/.crew/settings.json`. See `docs/adr/103-channel-norms.md`.
- **Super-agent: the milestones work as one system** (no new setting; each change sits behind a switch that already existed). A full-duplex bot's background job that ends in a folder Workers are working in now reaches them between their steps, without a Router decision. Recall resolves a job's id for the Workers that got its result, and the Watchdog's actions, ticks and watches (`wa_…`, `wt_…`, `ww_…`, `watchdog`) for the chat they concern, so a Router or Worker can see why the Watchdog stepped in; a Watchdog note names its action. The Watchdog reads the audit log next to the friction log: it notices an agent the command guard keeps refusing, and failed runs of drafts you approved. Background job output, recalled environment content and everything the Watchdog reads from outside are labelled untrusted like page text, and the Watchdog's and the Router's sessions get the same command guard hook as every other agent session; the audit log names a background sub-task's job. ARCHITECTURE.md describes the whole Super-agent mode, its switches and what each costs. See `docs/adr/010-integration-notes.md`.
- **Super-agent, milestone 9: a local model gateway** (Settings → Model gateway, off by default; off, the model connection works as before). Several providers and accounts at once, addressed as `provider/model`; routing groups whose next member answers when one hits a rate limit, an outage or a quota error, streams included; per-role routes (Router, Workers, Watchdog, speculative Workers, background calls) and per-bot picks through the bot's model setting, so the Router and the Watchdog can run on a light group and Workers on the strongest; rolling spend windows answered with 429 and Retry-After before any provider is asked; a usage log of every call with the provider that answered, tokens, estimated cost and latency; optional masking of keys, passwords and emails in prompts, restored in replies. It listens on 127.0.0.1 only and keys stay in `~/.crew/settings.json`. See `docs/adr/009-model-routing.md`.
- **Super-agent, milestone 7: lifecycle skill families, a command guard and draft-only external actions** (Settings → Safety; see `docs/adr/007-lifecycle-skills.md`). Built-in skills for triage, reproducing a report as a failing test, drafting a fix, structured self-review and adversarial review, release preparation and read-only repo-health audits, grouped in families that each project opts in to; the Router can hand a family's skills to a Worker, and Workers on read-only families cannot edit files. A deterministic command guard, on by default, refuses reading credential files, pushing or posting in your name, and network tools outside the sandbox's allowed domains, in every permission mode; read-only commands no longer ask, and approval cards list what a command changes. Pushes, pull requests, issues, comments and messages become drafts you approve with one click, shown with the exact command and target; a Drafts bar sits above the composer next to the Workers and Background jobs bars. Agent sessions (bots, Workers, Routers, the Watchdog, sub-tasks) and a full-duplex bot's background commands no longer receive tokens and keys from Crew's environment unless a project passes one through; with the model gateway on, the only credential left is the session's own gateway token. A background job's command passes the guard exactly as a Bash call would. Page text, console output, fetched pages, the Router's environment events and events delivered straight to Workers are labelled as untrusted in prompts. An opt-in audit log records every drafted action, its approval, what ran and how to reverse it.
- **Super-agent, milestone 6: the Watchdog** (Settings → Super-agent → Watchdog, off by default; off, nothing runs). A session outside the chats, on a timer, checks Workers' progress (stuck, looping, drifting, failed), approvals waiting for you, turn errors, friction and interface errors. Rules in code decide whether to look at all, so a healthy tick calls no model. It can nudge, stop or restart a Worker (a new session from a recap that keeps its thread subscriptions), tell a chat, and re-check transient failures until they heal; it never does the work or answers approvals. Hard limits: ticks per hour, actions per tick, budget per day. With the model gateway on, its calls go out under the gateway's Watchdog route and spend windows. The Watchdog page shows its state, usage, actions and watches, and has a chat to ask it why something failed; changes it proposes to trigger policies or a bot's role apply only when you accept them. See `docs/adr/006-watchdog.md`.
- **Super-agent, milestone 5: Inline & Spill context and the chain of recall** (Settings → Super-agent → Chain of recall, off by default; off, prompts and tools are as before). Every message, trigger, thread, Worker and the environment are injected with their id; the focus of a turn is sent generously, what sits next to it its first words, everything else one line, and the rest stays behind a `recall id=…` handle. Bots, Workers and Routers get a `recall` tool (it replaces `chat_history`) whose result lists the ids of related objects, so they can follow a trigger to its thread and on to its Workers. With direct routing on, a thread lists its subscribed Workers, a Worker the threads it subscribes to, and a trigger the Workers it went straight to; an event delivered to a Worker and cut short names its `recall` handle. Each turn logs and keeps how many tokens it injected, with and without the rules. With full duplex, background jobs can be recalled by their `job_…` id too, and a job result that starts a turn is kept whole, since it is already cut to the head and tail of its output. See `docs/adr/005-chain-of-recall.md`.
- **Super-agent, milestone 4: full duplex** (a per-bot switch, off by default; off, the bot works as before). A full-duplex bot gets `start`, `stop` and `status` tools: a long command or a sub-task runs in the background and the tool returns at once with a job id; when the job ends, its result (head and tail of the output, the full log readable by id) is posted in the chat and the bot gets a new turn for it. Commands pass the same approval gate, blocked actions and sandbox as a Bash call. Messages sent while the bot works reach it after its current step. A Background jobs bar above the composer shows each job with its log and a Stop button. Workers and the Router do not get the tools; with the model gateway on, sub-tasks and sandboxed commands are billed to the bot's own route and spend windows. See `docs/adr/004-full-duplex.md`.
- **Super-agent, milestone 3: thread subscriptions and direct routing to Workers** (Settings → Super-agent → Router and Workers → Direct routing to Workers, off by default; off, every event goes through the Router as before). A Worker subscribes to the threads it works on: the chat's workspace, which it shares with the chat's other Workers, and any routine whose run it was dispatched for. Later events there go straight to it with no Router call: a routine's next run wakes it, while console errors, files edited by hand and other Workers' merges reach Workers that are already working at their next step. A Worker can hand an event back to the Router or unsubscribe, and so can you, from its transcript dialog. The Workers bar counts the Router decisions this avoided. See `docs/adr/003-subscriptions.md`.
- **Super-agent, milestone 2: a resident Router and isolated Workers** (Settings → Super-agent → Router and Workers, off by default; off, group chats work as before). Each group chat gets a Router that receives every message and event, replies in at most 100 words, and dispatches Workers; it has no file or shell tools. Each Worker does one task in its own Claude Code session and git worktree, as a chat member with that member's permissions, editable paths and budget, on the strongest model, and reports to the Router; Crew merges its changes into the chat's branch. Events that arrive while the Router thinks are handled together in its next turn. A Workers bar above the composer shows each Worker's status and last report, with its transcript, Stop and Dismiss. See `docs/adr/002-two-layer.md`.
- **Super-agent, milestone 1: triggers, threads and two-stage filtering** (Settings → Super-agent, off by default; off, Crew behaves as before). User messages, routine runs, turn results, outside edits and preview console errors become triggers in threads; per-source rules in code settle most of them and a cheap model decides the rest from your written policies. An "act" decision is a short note only you see. A new Triggers page lists the events live and opens each one with its full content and related events. See `docs/adr/001-triggers.md`.
- **REA reverse engineering plugin** in the plugin library: see how a feature on a website or in a JavaScript/Electron app works without its source. A new `browser_debug_target` tool gives the bot the DevTools endpoint and target id of its `browser_act` page, so REA's web tools can inspect that page. Crew's headless Chrome now listens on a loopback-only debugging port for this.

### Changed

- The project is now English-only: UI, agent prompts, docs and code comments. The default UI language is English, and `@all` (or `@everyone`) mentions everyone in a group chat.
- The desktop build downloads Electron and the AppImage tools from their official sources; set `ELECTRON_MIRROR` / `ELECTRON_BUILDER_BINARIES_MIRROR` to use a mirror.

## [0.2.0] - 2026-10-02

The first official release. Renamed to Crew, with isolated workspaces, a sandbox, adversarial review and a set of "improve from use" mechanisms, plus the engineering groundwork.

### How you work

- **Isolated workspaces**: a chat can work in its own git worktree and branch. Each turn is auto-committed; see the diff against the main branch under "Changes" and squash it into one commit to merge back in one click. New commits on the main branch can be synced in, and conflicts can be handed to an agent to resolve. A new workspace brings along local files that git does not track but the work needs (`.env`, `CLAUDE.md`, settings and hooks in `.claude/`, files in `.git/info/exclude`). Projects can configure a setup command, commit message requirements, no AI attribution, and actions that always need confirmation.
- **Composer toggles** (like Claude Code): switch the permission mode, model and thinking effort per chat; switching the permission mode takes effect immediately on the turn in progress. A small ring shows context usage; the bottom of each reply shows the model actually used.
- **Other model providers**: DeepSeek, Kimi, Zhipu GLM, Qwen, MiniMax, OpenRouter, Ollama, or any endpoint compatible with the Anthropic API.
- **File changes made outside the chat are announced in the chat**: when project files are changed by hand, by another editor, by git operations or by Crew's code editor, the chat gets a message saying which files and which lines changed; blind-review agents see it too.
- The browser's back / forward buttons switch between chats, and `#/chat/<id>` links open a specific chat directly.

### Security

- **Sandbox** (on by default): commands run by agents are confined to Claude Code's sandbox (bubblewrap); they can only write to the project directory, the network can only reach localhost and allowed domains, and hosts not on the list are rejected outright. Agents cannot turn it off themselves. Requires bubblewrap and socat on Linux.
- **Blocked actions**: enforced at every permission level, including full auto (they match command text and only prevent accidents; the real boundary is the sandbox).
- Approval cards explain why they ask: which "always ask" rule (the agent's or the project's) and which permission level. "Always allow" adds a rule for every segment of a compound command, and read-only commands such as `cd`, `cat` and `grep` no longer need confirmation.
- The API validates requests at the entry point; invalid ones get a 400 that names the field.

### Roles and cost

- **Roles tied to cost and permissions**: Pixel / Forge / Muse use Sonnet, Quill uses Haiku, Lens is read-only, Probe can only edit test files, Chief uses the strongest model. Each agent can have "paths it may edit" and a "monthly budget"; the agents page shows how much each role spent this month.
- **Per-turn trace**: click "Trace" at the bottom of a reply to see, for each model call, how many tokens were read, how many were cache hits, how many were written, and which tools were called. The data is read from Claude Code's own session transcripts.
- **Saving money**: each turn sends only new content (older long messages are shrunk to one line, with `chat_history` for the full text; environment info is sent once per session); acceptance and review roles use a new session every turn; other sessions switch to a new session past 60k tokens, carrying the last 12 messages; one-shot model calls no longer carry Claude Code's built-in 29k tokens.

### Checking and refutation

- **Skeptic adversarial review**: receives only the user's request and the diff of the changes, never the teammates' explanations; its job is to try hard to refute the change, and only reproducible counterexamples count. Invoked with `/challenge`; can be used as a gate before merging; can also trigger automatically by fixed rules (changes to styles, permissions, dependencies and similar files, or more than 150 lines; at most twice per request).
- **Lens reviews blind too**: it cannot see teammates' explanations or acceptance verdicts; where real testing is needed it writes "needs real testing".
- **Browser tools support dark mode** (`colorScheme: dark`), and colors are read from real computed styles.

### Improving from use (every step needs your approval)

- **Improvement suggestions**: reads recent turns, costs, refutation results and your earlier decisions, and proposes at most 3 small changes to agent settings, each of which must cite things that really happened in at least two different requests. You can edit before accepting, reject (with a reason) or withdraw; after accepting, performance before and after is compared.
- **Learned skills** (inspired by Hermes Agent): turns that did a fair amount of work, completed smoothly and were not refuted can be drafted into skills. Drafts go through fixed safety checks first and are saved only when you accept; drafting takes your earlier rejection reasons and edits into account.
- **Memory nudge**: after a complex turn, the agent is reminded to write down experience that will be useful later, recording only what the user said and what it verified first-hand.
- **Group chat routing (shadow mode)**: for messages without an @, Haiku guesses who should take them, once in each of two orders, and only records the guess without acting on it; once enough data accumulates, an accuracy lower bound and AUROC decide whether it can be trusted.

### Changed

- Renamed to **Crew**. The first launch moves `~/.vibecrew` to `~/.crew` and `~/VibeCrewProjects` to `~/CrewProjects`.
- The UI and icons are now black, white and gray with line icons; Settings → Appearance offers 6 logos, and the Dock, tray and window icons follow.
- In auto mode, agents no longer ask for consent in the chat for routine work.

### Reliability and engineering

- When Crew is restarted after being killed, the interrupted turn keeps its half-written content; the data directory has a format version and migrations, with an automatic backup before migrating.
- Tests: Vitest (unit and integration, including real Claude Code against a local fake model) and Playwright (browser and desktop app), over 200 in total; tests never touch real Crew data or the Claude login.
- Biome formatting and lint; GitHub Actions CI (also runs nightly against the latest Claude Code); pushing a `v*` tag publishes the AppImage automatically.
- Unified server logging; ARCHITECTURE and CONTRIBUTING docs; a `docs/mindmap.md` mind map of the development history.

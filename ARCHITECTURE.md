# Crew architecture

Crew runs a team of AI agents on your own machine: a Node server drives Claude Code sessions, and a React UI shows them as chats next to a live preview, files, a terminal and the changes. This document covers the parts Crew is made of, how a message becomes an agent's reply, and the design decisions that are easy to trip over. For usage see the [README](README.md); for the development workflow see [CONTRIBUTING](CONTRIBUTING.md).

Crew works in two ways, and you choose per switch:

- **Plain Crew** (the default). You write in a chat; one bot answers at a time; in a group chat the lead answers or hands off with @-mentions; nothing happens unless you write or a routine runs.
- **Super-agent mode** (opt-in). A group chat becomes one agent you talk to. It takes events from anywhere (your messages, routines, test runs, console errors, files edited by hand), settles most of them with rules in code, answers you in a few words, runs several tasks at once in isolated **Workers**, watches its own progress with a **Watchdog**, and recovers after a crash. It is a set of switches, all off by default: with all of them off Crew starts no extra process, writes no extra file and makes no extra model call. [Super-agent mode](#super-agent-mode) explains it from the top, with what each switch turns on and what it costs; each part then has its own section.

## The journey of a message

1. The UI calls `POST /api/chats/:id/messages`; `orchestrator.sendUserMessage` stores the message and decides who replies: the @-mentioned agents, or the lead when nobody is @-mentioned in a group chat. (In two-layer mode a group chat's message goes to its Router instead, and steps 2-7 below happen in Workers; see [Router and Workers](#router-and-workers-super-agent-two-layers).)
2. Each chat has one queue, and only one turn runs at a time (`withChatLocked`). Until a new workspace's setup command finishes, messages wait in line (`holdTurns`). (A full-duplex bot runs long commands in the background instead of blocking its turn, and reads messages that arrive meanwhile after its current step; see [Full duplex](#full-duplex-background-jobs-super-agent).)
3. `BotSession` in `agents/session.ts` keeps one Claude Agent SDK session per "chat x agent", so earlier context can be resumed. Agents with `freshSession` on (acceptance and review roles) start a new session every turn: a resumed session rereads the whole history on every call, which is wasted money for roles that only look at the current state. For the other agents, once a session exceeds `rotateAtTokens` (60k tokens by default), the next turn also switches to a new session, carrying the last 12 messages (`rotateSession` + `recapPrompt`). It calls the locally installed `claude` CLI (`vendor/sdk-binary-stub` replaces the SDK's bundled 240 MB binary).
4. The SDK's streaming events are turned by `agents/stream.ts` into the parts of a chat message (text, thinking, tool calls, approval cards) and broadcast through `bus`; `index.ts` pushes them to every WebSocket connection.
5. When a turn ends, Crew records which files it changed (undoable), which model it used, the context usage (the small ring next to the composer), and where the turn sits in the Claude Code session transcript (`meta.trace`: session id + time window). In an isolated workspace, the turn's changes are auto-committed to the branch.
6. "Trace" (`server/trace.ts`) reads `~/.claude/projects/<cwd>/<session>.jsonl` on demand and turns the lines inside the time window into a timeline: the lines of one API call (thinking, text, tool calls) are merged into one step with its token usage; tool results and sent prompts are one step each. Crew does not copy this transcript, so once it is cleaned up the trace is gone, and the UI says so plainly.
7. If an agent's reply @-mentions a teammate, the work is handed off to that teammate, with a cap on the count to prevent ping-pong.
8. Sessions are resumed, so anything sent stays in context; each turn therefore sends only what is new: environment info is sent in full the first time, after that only changes are sent, compared as "label: value" (`contextDelta`); older long messages in group chats are collapsed into one-line summaries, and agents fetch the full text by number with `chat_history`. (With the chain of recall on, these become one set of Inline & Spill rules and the `recall` tool; see [below](#chain-of-recall-super-agent-inline--spill).)

## Permissions

Permission levels are defined in `shared/types.ts`, the decision logic is in `agents/permissions.ts`, and the approval flow is in `orchestrator/permissionGate.ts`:

| Level | Claude Code mode | What Crew adds |
| --- | --- | --- |
| Read-only `plan` | plan | Chat-level settings cannot change it either |
| Ask every step `ask` | default | Every tool call pops an approval card in the chat |
| Auto-edit files `edits` | acceptEdits | Harmless commands (`cd`, `pwd`, `cat`...) are allowed straight away |
| AI reviewer `review` | auto | Claude Code's classifier decides |
| Full auto `auto` | default | `canUseTool` allows everything |

In addition, each agent can have "paths it may edit" (`editScope`, globs relative to the project): an Edit/Write outside that scope is rejected outright and the agent is told to @-mention a teammate. This is a hard constraint on the division of roles, not a prompt. The monthly budget (`monthlyBudgetUsd`) accumulates the per-turn cost reported by Claude Code (`server/usage.ts`); once it is used up, `runTurn` skips that agent's turns and says so once in the chat.

Whatever the level, the following three layers always apply:

- **Sandbox** (`server/sandbox.ts`): when on, every session gets Claude Code's `sandbox` option, commands run in bubblewrap, and the network reaches only localhost plus allowed domains (global list + project list). `allowUnsandboxedCommands: false`, so agents cannot escape with `dangerouslyDisableSandbox`; `autoAllowBashIfSandboxed: false`, so Crew's own approval logic still applies. This is the only layer that decides by "can it connect" rather than "what does the command look like", so it is also the only one that counts as a security boundary. All connections in the sandbox go through Claude Code's proxy (the proxy holds the allowlist; `strictAllowlist` makes hosts not on the list get rejected outright, rather than turning into a prompt that might be approved). But the sandbox's own `no_proxy` sends loopback and private addresses direct, and a direct connection reaches nothing inside the isolated network namespace, so to reach a service on this machine or the LAN, a command must be prefixed with `env -u no_proxy -u NO_PROXY` (the prompt already tells agents this). When the machine lacks the dependencies (bubblewrap and socat on Linux), the Settings page warns, and agents run without the sandbox.

- **Blocked actions** (`denyRules` in settings): written into the SDK's `permissions.deny` and also intercepted again by a PreToolUse hook without a matcher, so they cannot run even in full auto.
- **Command guard** (`server/guard.ts`, `settings.safety.guard`, on by default): fixed rules run by that same hook, after the deny list, so they hold in every mode, and in every agent session: chat bots, their background sub-tasks and job helpers, Workers, the Router and the Watchdog (the last two have no built-in tools; the hook is there so the rules never depend on that). It decides by what a command *is*, not by its text: it splits compound commands, looks through wrappers (`env`, `sudo`, `timeout`, `xargs`, a path to the binary), into `bash -c`, `eval`, `$(…)`, backticks and `find -exec`, and past git's global options. It refuses credential files (`~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.netrc`, Crew's own `settings.json`…) in any tool, actions in the user's name (`git push`, writing `gh`/`glab`/`hub` subcommands, publishing, `curl` sending data off this machine), and network tools reaching hosts outside the sandbox's allow-list (`curl`/`wget` to unlisted or unreadable hosts, `ssh`/`scp`/`nc` to anything but this machine). See [Safety](#safety-lifecycle-skills-drafts-and-the-guard).
- **Actions that always need confirmation** (each agent's rules, plus the project's `askRules`): always pop an approval card. A compound command (`a && b`) is allowed only if every segment matches an "auto-allow" rule.

## Changes made outside the chat

Agents only know what was said in the chat. `server/outsideEdits.ts` watches project files: when a change happens while no agent is working in that project (`projectBusy`), Crew itself is not writing (`quietWrites.ts`: workspace git operations, setup commands and undoing a turn mark the project "quiet", plus 4 more seconds afterwards), and dependencies are not being installed, it waits 3 seconds and merges the batch of changes into one system message (`notice: 'outside-edit'`), sent to every chat on that project. For text files it says which lines changed: compared with the content Crew last saw, or with the last git commit if it never saw the file. Blind-review agents see these messages too.

## Super-agent mode

Without it, a chat is a set of manual sessions: one bot answers at a time, nothing happens unless the user writes, and the user follows every session. Super-agent mode (design notes in [docs/superagent](docs/superagent/design-notes.md), decisions in [ADRs 001-010 and 105](docs/adr/)) turns a group chat into one agent the user talks to, which is **continuous** (one Router keeps the chat's context), **efficient** (Workers run tasks in parallel, in their own worktrees, and long commands run in the background), **proactive** (events from the environment are filtered and acted on, quietly by default, and in projects that opt in a reported problem is reproduced and fixed in the background before anyone asks) and **durable** (a Watchdog outside the chats notices stuck or failed work, and a restart recovers what was in flight). It is a set of switches, all off by default; with all of them off Crew starts no extra process, writes no extra file and makes no extra model call, after a restart too (`tests/integration/super-agent-off.test.ts`).

### The parts in one minute

- **Trigger bus** (`triggers/`): every event becomes a small record (a Trigger) on a Thread of related ones. Rules in code settle most of them (the fast path); a cheap model judges the rest against policies you write (the slow path).
- **Router and Workers** (`layers/`): each group chat gets a resident Router that reads everything needing a decision, answers you in at most 100 words and dispatches Workers; each Worker does one task in its own session and git worktree, as one of the chat's members, and its work is merged into the chat's branch.
- **Direct routing**: a Worker subscribes to the Threads of its task (its folder, its routine) and gets their events between its steps, with no Router decision.
- **Full duplex** (`jobs/`, per bot): long commands and sub-tasks run in the background; the result comes back as a new event.
- **Chain of recall** (`recall/`): every injected object carries an id, prompts stay small, and a `recall` tool walks from any id to its neighbours.
- **Watchdog** (`watchdog/`): a timer outside the chats; rules flag stuck, looping or failed Workers and other trouble, and only then does a session look and nudge, stop or restart, within hard limits.
- **Model gateway** (`gateway/`): every session's calls go out under its role, with failover between providers and accounts and spend windows.
- **Safety** (`guard.ts`, `drafts.ts`, `audit.ts`): a command guard in every session, actions in your name only as drafts you approve, credential-free environments, an optional audit log. On by default except the audit log, and not tied to the other switches.
- **Speculative execution** (`speculative/`, per project): a failing check, a console error or a bug report may start a silent Worker in a throwaway worktree; Crew verifies its fix with the project's checks and shows only a verified one, as a card with a one-click merge.

### One event through the whole system

1. **An event arrives** from any path that already handled it: a user message, a routine run, a turn's result, files changed outside the chat, a preview console error, a background job ending, a Worker's merge. It is published as a Trigger on a Thread (`chat:`, `routine:` or `workspace:`).
2. **The fast path** (rules in code) settles most of them. Explicit requests go to the chat as always. A Trigger on a Thread that Workers subscribe to goes straight into their inboxes. Filtered sources pass allow-lists, noise rules, cooldowns, de-duplication and an hourly budget; what is left is a candidate.
3. **The slow path** asks a cheap model, with the user's policies, about candidates in batches; "act" means a short note for the user, or an environment event in the Router's inbox.
4. **The Router** of a two-layer chat takes everything that needs a decision in batches: the user's words, routine runs, Workers' reports, environment events (which cannot start work), and a `<direct>` list of what went to Workers without it. It replies in at most 100 words and dispatches, messages or stops Workers; it never executes.
5. **Workers** each do one task in their own session and worktree with full tools, subscribe to the Threads of their task (its routine, the chat's workspace), and between their steps read what arrives there: another Worker's merge, a console error, a hand edit, a background job someone ran in the same folder. When a turn ends Crew merges their branch into the chat's branch and reports to the Router.
6. **Long commands** in a full-duplex bot's turn run as background jobs; the result comes back to that bot as a new event, and to the Workers working in the same folder as an environment event.
7. **Speculative runs** start, in projects that opted in, when fixed rules read a Trigger as a failing check, a preview console error or a user describing a problem without asking for the fix: a Worker in a throwaway worktree tries to reproduce it and fix it, unattended and quiet. Crew runs the project's check command itself (it must pass with the fix and fail without it); only then is the fix shown in the chat, with its diff and a one-click merge, and a two-layer chat's Router hears of it as an environment event. Anything else is discarded without a word.
8. **The Watchdog** ticks on a timer outside every chat. Rules in code flag stuck, looping or failed Workers, waiting approvals, turn errors, friction, interface errors, the guard refusing one agent again and again, and failed draft runs; only then does its session look and nudge, stop, restart or notify, within hard limits.
9. **Recall** connects it all: every injected object carries its id (`#12`, `tg_…`, `th_…`, `wk_…`, `job_…`, `wa_…`, `wt_…`, `ww_…`), and `recall` walks from any of them to its neighbours inside the caller's chat.
10. **Underneath**, every agent session (chat bots, sub-tasks, Workers, speculative runs, Routers, the Watchdog, job helpers) runs through the same deny hook (blocked actions, then the command guard), gets a credential-stripped environment, and reads outside text inside `<untrusted>` blocks; with the model gateway on, each session's calls go out under its own role (`bot`, `worker`, `speculative`, `router`, `watchdog`, `oneshot`) to its own route and spend windows.

### Where the parts meet

The milestones were built apart; [ADR 010](docs/adr/010-integration-notes.md) lists each seam, how it is wired and its test (`tests/integration/seams.test.ts`): a job's result reaches the Workers subscribed to the folder it ran in; recall resolves job ids for the Workers that got their result, and the Watchdog's actions, ticks and watches for the chat they concern; the Watchdog reads the audit log beside the friction log; per-role routing covers the Router, Workers and the Watchdog; the `<untrusted>` wrapper and the command guard apply to Workers, background jobs and the Watchdog alike.

[ADR 105](docs/adr/105-hardening.md) walks the whole flow with every switch on (`tests/integration/super-agent-flow.test.ts`, in demo mode and with the real Claude Code through the gateway; `tests/e2e/super-agent.spec.ts` in the browser) and fixed what broke there: Crew's own MCP servers set `alwaysLoad` so Claude Code's tool search never hides `recall`, `hand_back`, `start` or `chat_history` (and the Router and the Watchdog, which have no other tools, run with tool search off); summaries keep the ids they name (`preview()` no longer strips `_` inside a word); the Watchdog's `restart_worker` is refused for a Worker a restart cut off, one the user stopped, or one the Router already replaced for the same request (`watchdog/duplicates.ts`).

### After a crash

Every part recovers or fails cleanly on start, and nothing is done twice ([ADR 105](docs/adr/105-hardening.md), `tests/integration/restart.test.ts`):

- **Workers** cut off mid-turn are stopped (`Crew restarted`), their worktrees committed, their Routers told; they keep their subscriptions, and a Worker the Router resumes receives its Threads' events again.
- **Routers** get again the user's messages past their cursor, and (`layers/recovery.ts`, read off the Router's own log) the messages a turn cut off by the crash took without dispatching anything, plus Workers' reports no finished turn read. A re-handed event says so, and a cut-off one tells the Router to check its Workers before dispatching. What a Worker was already dispatched for is not handed again; what the user stopped is not either.
- **Background jobs** are marked stopped and their output posted without a turn; a command still running in its own process group is stopped first (`jobs/orphans.ts`, matched by its recorded process group and start time).
- **The Watchdog** settles a tick or a maintainer's question the crash cut off (`watchdog/recovery.ts`): the next tick looks at the same window, the question's log says to ask again, and watches on Workers the restart cut off are closed.
- **Triggers** still waiting for the slow path are marked `interrupted`; the gateway starts on a new port, which new sessions pick up.

### The security model across the mode

It follows Apache Magpie's principles, applied to every layer at once:

- **External content is data.** Page text, console output, fetched pages, event payloads, background job output, recalled environment objects, a speculative run's signal and every outside text in the Watchdog's snapshot are inside `<untrusted source="…">` blocks the text cannot close; every system prompt (bots, Workers, the Router, the slow path, the Watchdog) says what they mean. An environment event cannot start work through the Router: its gate refuses dispatch for environment-only batches, and subscribed Workers only receive environment events while already working. The one exception is deliberate and narrow: in a project that opted in, fixed rules may start a speculative run, which works unattended in a throwaway worktree (what would ask is refused), cannot reach the user or draft anything, and changes the user's files only through a merge the user clicks with the diff in front of them.
- **Nothing is sent in the user's name.** Pushes, pull requests, issues, comments and messages are drafts; only the user's click runs them.
- **Confined before it reads anything real.** The sandbox (the only real security boundary), credential-stripped environments for every agent session, and the deterministic command guard in the deny hook of every agent session, including the Router and the Watchdog, which have no built-in tools at all.
- **Confirmations are budgeted, gates are deterministic.** Reads never prompt; a change prompts once with what it changes; every limit (Workers per chat, hops, jobs, ticks, actions, budgets, word counts) is checked in code, not asked of a model.
- **Audited.** With the audit log on, every draft, approval, run and guard refusal is a line naming the bot, chat, Worker or job; the Watchdog reads it and flags an agent that keeps trying what the guard refuses.

Speculative execution (milestone 8, [ADR 008](docs/adr/008-speculative.md)) was built after the integration: it reuses the Worker layer, the Trigger bus's listener hook, the job runner, the gateway's `speculative` role and the skill families' `speculative` mode; see [below](#speculative-execution-super-agent-silent-reproduce-and-fix).

## Triggers and threads (Super-agent, preview)

The first step towards one always-on agent that watches events and acts on them without being asked (design: [ADR 001](docs/adr/001-triggers.md)). Everything here is behind `superAgent.enabled` in settings, off by default; while it is off, `publishTrigger` returns at its first line, nothing is recorded and no folder is created.

- **One stream of events.** The paths that already handle Crew's inputs each publish a **Trigger** as the event happens: `sendUserMessage` (a user message), `runRoutine` (a routine run), the end of `runTurn` (a turn result), `outsideEdits.flush` (files changed outside the chat), `deliverJob` (a full-duplex bot's background job ended, on the chat's thread for the bot that started it, and again on the workspace thread of the folder it ran in when Workers subscribe to it; see [below](#full-duplex-background-jobs-super-agent)), and the preview's console errors, which the browser tab forwards to `POST /api/triggers/preview-console`. A Trigger is small: an id, a source, a one-line summary, the ids of related objects, and a `ref` to its full content (a chat message, a routine, or a payload file). They keep doing what they did before; the Trigger is a record of the event, plus a decision.
- **Threads.** Each Trigger joins a **Thread** by key: `chat:<id>` (one topic; "Start new topic" closes it), `routine:<id>`, or `workspace:<projectId>` (outside edits and console errors). A turn's result joins the thread of whatever started it and points back at that request.
- **Fast path** (`triggers/fastPath.ts`, pure): a Trigger on a thread that Workers subscribe to goes straight to them (rule `subscribed`; see [Thread subscriptions](#thread-subscriptions-and-direct-routing-super-agent)); otherwise explicit requests (user messages, routine runs, a bot handing off, a job result going back to the bot that started the job) are acted on by the chat as always; per-source rules drop the rest unless they are worth a look. Each filtered source (turn results, outside edits, console errors) has a mode (`candidate`, `explicit` only, or `ignore`, which records nothing), an allow-list, plus a project allow-list, noise patterns, a per-thread cooldown after a notice, de-duplication by fingerprint, and an hourly budget.
- **Slow path** (`triggers/slowPath.ts`): the candidates go to Haiku through the same bare `oneShot` call shadow routing uses, with the **policies** the user writes in Settings. One call runs at a time; candidates that arrive meanwhile are decided together in the next call (up to 8). Each event is inlined small (summary, first ~50 words, the thread's previous events by id) and fenced as data; an unusable answer means "stay quiet". Demo mode uses a deterministic stand-in.
- **Acting** is a short UI-only note in the related chat (`notice: 'trigger'`, at most 100 words) plus a toast. Bots never see it, and nothing runs on its own. A chat in two-layer mode gets the decision in its Router's inbox instead, as an environment event that cannot start work (below).
- **Seeing it**: the Triggers view (sidebar, only while the feature is on) lists events live (`ServerEvent` `trigger`), with filters by source and verdict; opening one shows its payload and links to related and same-thread triggers (`GET /api/triggers/:id`). `GET /api/triggers` is the debug endpoint.

## Router and Workers (Super-agent, two layers)

The second step (design: [ADR 002](docs/adr/002-two-layer.md)): global continuity and parallel execution are split. Behind `superAgent.router.enabled`, which only counts while `superAgent.enabled` is on; both are off by default. The one check is `routerMode(chat)` (group chats only) at the two entry points, `sendUserMessage` and `runInChat`; with it false, nothing below runs and group chats route to the lead as before. Direct chats are never affected.

- **Router** (`layers/router.ts`): one resident Claude Code session per group chat, speaking as the chat's lead, on `superAgent.router.model` (Sonnet by default). Every event in the chat that needs a decision goes into its inbox: the user's messages (with whom they @-mentioned), routine runs, Workers' reports, and Trigger decisions the slow path acted on (with direct routing on, events on threads its Workers subscribe to go to them instead; see [below](#thread-subscriptions-and-direct-routing-super-agent)). It runs one turn at a time; events that arrive meanwhile wait and all go into the next turn together (`BatchQueue`), so one call makes several decisions. It never executes: the session has no built-in tools (`tools: []`), a short system prompt of its own instead of Claude Code's, no settings files, and a `canUseTool` that refuses anything but its own tools. Those are `crew_router` MCP tools (`layers/tools.ts`): `dispatch_worker`, `message_worker`, `stop_worker`, `list_workers` and `reply`. Only `reply` reaches the chat, as a bot message from the lead marked `router`. The Router's turns are kept as messages in their own log (`rt_<chatId>` in `messages/`), with the ids of the events each turn handled (`batch`). Every Router runs in one fixed folder (`CREW_HOME/router`), so a chat moving into its workspace does not cost it its Claude Code session. Changing a chat's switches, a bot or the sandbox refreshes Worker sessions as it does chat sessions; idle ones close after 15 minutes.
- **The batch prompt** (`layers/prompts.ts`, pure) follows Inline & Spill: a `<workers>` line per Worker, then one `<event>` per item with its id. The user's words are inlined in full (cut at 4,000 characters), a Worker's report to its first ~80 words with `list_workers id=…` as the way to read the rest, and environment events as fenced data. A Router session that outgrows `rotateAtTokens` starts over with a recap of the chat's latest messages.
- **Gates in code** (`layers/gates.ts`): a batch made only of environment events cannot dispatch or message Workers (ADR 001's open risk: an event must not start work with full tools), and environment events are never batched with explicit ones, so the gate holds per event. `reply` refuses more than 100 words. Only chat members can be dispatched, not past their monthly budget; at most `maxWorkers` (3) Workers may be active per chat, and at most the chat's `maxHops` started per user message. Without a workspace of their own, only one Worker at a time may work in the chat's folder, and a Worker whose workspace is gone never runs elsewhere.
- **Workers** (`layers/workers.ts`): `dispatch_worker` returns at once with the Worker's id, and the Worker starts in the background. It runs as a member of the chat (the one the Router names, by default the lead), so it has that member's role description, permission level (with the chat's switch applied, as for any turn), `editScope`, allow/ask rules, plugins and budget, through the same `BotSession`, `permissionGate`, sandbox and deny rules as a chat turn. Its model is the chat's model switch, else `superAgent.router.workerModel`, else the default model. Its prompt holds the Router's task and the user's own messages from the dispatching batch (a blind reviewer gets its blind prompt with the chat branch's diff instead). Its system prompt says it reports to the Router and never @-mentions anyone, and it gets no `notify_user`. Its turns are kept in its own log (`wk_…` in `messages/`), and approval cards appear there; the Workers bar marks it "Needs you" and the usual notification fires. Several Workers run at once, and the chat stays free while they work.
- **Workspaces and landing.** In a git project, the first dispatch moves the chat into its isolated workspace if it has none (`doCreate`, with its note and setup command). Each Worker then gets a worktree of its own branched from the chat branch's current commit (`createWorkerWorkspace`, sharing `addWorktree` with chat workspaces; the project's setup command runs there too). When a turn ends, Crew commits the Worker's worktree, and if the turn finished it **lands** the work: under the chat's lock (`whenChatFree`, which waits rather than refusing), it runs `git merge --no-ff` of the Worker's branch inside the chat's worktree. On conflict it aborts, leaves both branches as they were, and tells the Router, which can ask the Worker to merge the chat branch in (Crew adds the instructions to that follow-up). The user's project folder is untouched until the user merges the chat branch, as before. Without git, a Worker works in the chat's folder and its record says why.
- **Reports.** When a Worker's turn ends, its final text (cut at 6,000 characters), status and landing go to the Router as an event. A `turn` Trigger is also published on the chat's thread, which the fast path settles with rule `routed` (delivered directly, no model).
- **Control.** `message_worker` resumes a finished Worker's session, or queues the message for when its current turn ends. The chat's Stop stops the Router's turn, drops its inbox and stops every Worker without the Router replying. "Start new topic" resets the Router's session and dismisses finished Workers. Dismissing a Worker removes its worktree; its branch is kept if its work never reached the chat branch. Finished Workers are dismissed after 6 idle hours. Deleting the chat removes everything. Closing the chat's workspace, switching its project or deleting it is refused while Workers are active (`isChatBusy` counts the Router and Workers).
- **Switching back.** A message the two layers take (the Router, or Workers subscribed to its thread) moves every member's read cursor past it, so a chat switched back to its lead does not hand the lead those messages again as new ones and have it redo the Workers' tasks; they stay readable with `chat_history` (or `recall`).
- **Restarts.** A Worker record is written at once when it is created and on every status change. On start, Workers cut off mid-turn are marked stopped (`Crew restarted`), their worktrees are committed (`reconcileWorkspaces` keeps Worker workspaces whose Worker still exists), and their Routers are told. User messages past `Chat.router.cursor` (written at once when a turn takes them) are handed to the Router again.
- **Seeing it**: in a router-mode chat, a Workers bar above the composer shows the Router's state and queue, and each Worker's title, member, status and last report or landing. Each row opens that Worker's transcript (the chat's own message rendering, approval cards included); the bar also offers Stop, Dismiss and the Router log. The chat header and the composer's Stop button count the Router and Workers. API: `GET /api/workers?chatId=`, `GET /api/workers/:id/messages`, `POST /api/workers/:id/stop`, `POST /api/workers/:id/dismiss`, `GET /api/chats/:id/router/messages`; `ServerEvent` `worker`, `worker_deleted`, `router`.

## Thread subscriptions and direct routing (Super-agent)

The third step (design: [ADR 003](docs/adr/003-subscriptions.md)) keeps the Router off the hot path. It sits behind `superAgent.router.subscriptions` (off by default), which only counts in two-layer mode. With it off, no Worker subscribes, no landing Trigger is published and no prompt changes.

- **Subscriptions** live on the Worker (`Worker.threads`, many-to-many with Threads). At dispatch, a Worker subscribes to the `routine:` thread of each routine run in the batch; once its workspace is ready, it also subscribes to the chat's `workspace:` thread, which it shares with the chat's other Workers. `dispatch_worker` takes `subscribe: false` for one-off tasks. Blind reviewers never subscribe. Chat threads cannot be subscribed: they are the Router's channel to the user. Pruning keeps any Thread a Worker still subscribes to.
- **Receivers** (`layers/subscriptions.ts`, pure). A Worker receives a Trigger on one of its threads when it is not dismissed, did not cause the Trigger, its chat is in two-layer mode with the switch on, and either it is active or the Trigger is explicit and the Worker is `done`. So a routine run wakes a finished Worker, but environment events only reach Workers that are already working; they never start work.
- **Delivery.** In `publishTrigger`, the bus looks up the receivers before the fast path. With any, the fast path settles the Trigger as `subscribed`; the noise rules, "ignore" and "explicit only" still apply first, and a duplicate already delivered within 30 minutes is dropped. The Trigger records `filter.direct` and goes into each receiver's inbox (`Worker.inbox`, at most 20 items, Inline & Spill: summary and first ~60 words, or a routine's prompt in full). Neither the cheap model nor the Router is called. For routine runs, `runInChat` takes a `publish` callback from `runRoutine` and skips the Router when the run went direct.
- **Into the session.** While a turn runs, the session's `PostToolUse` hook (`SessionConfig.deliveries`, beside the wrap-up note) takes the inbox at the next tool call of the main loop and adds it as `additionalContext`, fenced as `<event>` data, an environment event's text inside the `<untrusted>` wrapper (see [Safety](#safety-lifecycle-skills-drafts-and-the-guard)). A new turn's prompt carries whatever is left, and the first turn lists the Worker's threads. When a Worker goes idle with unread items, an environment Trigger nobody else read goes back to the normal path (rules, cheap model, Router), and a routine run goes to the Router. A chat Stop drops them.
- **Landings.** After Crew merges a Worker's branch into the chat's branch, it publishes a `landing` Trigger on the chat's workspace thread. It is built from facts (Worker, title, files, commit), never from the Worker's words. It goes only to the other active subscribers, so a Worker editing the same files can merge the chat's branch early; with no subscriber it is dropped (`no-subscribers`).
- **Background jobs** ([ADR 010](docs/adr/010-integration-notes.md)). When a [full-duplex](#full-duplex-background-jobs-super-agent) bot's job ends in a folder some Worker subscribes to (a chat's workspace, or a folder without git that a direct chat shares with a two-layer chat), `publishJobResult` publishes a second, environment `job` Trigger on that workspace thread: the job's line as its summary, and as its payload what ran and the last lines of its output (`tailDigest`, about 45 words, `recall job_…` for the rest). Like a landing it goes only to the active subscribers and is dropped with none; nothing is published while direct routing is off, nobody subscribes to the thread, or after a restart.
- **Leaving.** Workers get two `crew` tools: `unsubscribe_thread`, and `hand_back`, which unsubscribes and sends the event to the Router (once per Trigger, as a routine event or an environment event that still cannot start work). The user can unsubscribe a Worker from its dialog (`POST /api/workers/:id/unsubscribe`).
- **The Router observes.** Triggers that went straight to a chat's Workers are listed in the Router's next batch under `<direct>`, with no environment text, and never start a turn on their own. `<workers>` lines show each Worker's subscriptions. `Chat.router.decided` counts the events Router turns took. `Chat.router.direct` counts events that went straight to Workers (Router decisions avoided); a hand-back or an unread reroute takes the count back. The Workers bar shows it, the Triggers view counts `stats.direct`, and a restart hands the Router any routine runs left unread in Workers' inboxes.

## Full duplex: background jobs (Super-agent)

The fourth step (design: [ADR 004](docs/adr/004-full-duplex.md)): a long tool call no longer blocks the turn. Behind `Bot.fullDuplex`, a per-bot switch in the bot editor, off by default; with it off the bot gets none of the tools, its prompt does not mention them, nothing is injected mid-turn and `CREW_HOME/jobs/` is never created. It does not need the Super-agent switch (the Trigger it publishes is simply not recorded while that is off). Workers, the Router, the Watchdog and sub-tasks never get the tools: a Worker's turn ending is when its work lands, and the two layers already have their own async start (`dispatch_worker`).

- **Tools** (`jobs/tools.ts`, served by the `crew` MCP server and, in demo mode, called directly by `FakeSession`): `start` launches a shell command or a sub-task and returns at once with `Started job_…`; `stop` terminates one and returns its output so far; `status` lists the chat's jobs, shows one, or reads a slice of its log (`from`, `lines`).
- **Gates.** `startRefusal` (pure, `jobs/gates.ts`) refuses read-only bots, more than 4 running jobs per chat and odd timeouts (default 60 min, at most 720). Then the handler asks the **running turn's own** `permissionGate` about a synthetic `Bash` call with the same command, so deny rules, the [command guard](#safety-lifecycle-skills-drafts-and-the-guard) (its refusals, and its read/change verdict: a read starts without a card, a change's card lists what it changes), the bot's and the project's must-ask rules, allow rules and the permission level apply exactly as for Bash, approval card included (`review` asks, since Claude Code's classifier never sees an MCP call). A sub-task needs no approval to start; each of its tool calls goes through the bot's gate, with cards in its own transcript.
- **Running a command** (`jobs/runner.ts`). With the sandbox off or unavailable, Crew runs it itself with the dev server's process handling (`procs.ts`: `bash -c` in its own process group with the cleaned environment, no model credentials, and, like the bot's own Bash calls, none of the user's credentials while `safety.stripCredentials` is on, the project's `passEnv` excepted; stop is SIGTERM to the group, SIGKILL after 3 s). With the sandbox on, the command runs as a real Bash call in a helper Claude Code session that has only the `Bash` tool, the bot's sandbox options and deny rules, and a two-line system prompt; its `canUseTool` allows one Bash call and rewrites the input to the approved command (timeout capped at Bash's 10 minutes, foreground). Crew never spawns a command unconfined while the bot's own commands would be confined.
- **A sub-task** is one turn of a new session of the same bot (`sessionConfig(…, { subtask })`: no resume, no full-duplex tools, a "you are a background sub-task" section), run by the same `runLogged` as a Worker's turn and kept under the job's id in `messages/`. With the chain of recall on it gets `recall` in place of `chat_history`, like the bot's own session.
- **Model calls.** Sub-tasks and the sandboxed helper sessions are the bot's own spend: with the [model gateway](#model-gateway-super-agent) on they go through it under the bot's scope (`/s/bot/<botId>`), so the bot's routes and spend windows apply to them, and `usage.ts` counts sub-task logs toward the bot's monthly budget.
- **Output, Inline & Spill** (`jobs/spill.ts`, pure). A command's output goes to `CREW_HOME/jobs/<id>.log`, ANSI-free, capped at 5 MB. A result inlines the first 20 lines (1,500 characters) and the last 40 (3,000), with `… N lines omitted (read them with status id=… from=… lines=200) …` between, inside `<untrusted source="job output" job="job_…">` (`sub-task report` for a sub-task), the same wrapper as page text and event payloads; so are `status` slices of the log.
- **Delivery.** When a job ends (done, failed, stopped, timed out), `deliverJob` in the orchestrator posts the result as a system message (`notice: 'job'`, visible to the bots), publishes a `job` Trigger on the chat's thread (explicit, fast path rule `job-result`: chat threads have no subscribers), and queues a turn for the bot that started it (`MessageTrigger { type: 'job' }`). When Workers subscribe to the folder it ran in, they get it too, as an environment event on that workspace thread ([above](#thread-subscriptions-and-direct-routing-super-agent)). A job stopped by the bot itself, by the chat's Stop or "Start new topic" is not delivered again. In a chat that has since switched to two-layer mode, the result is posted without starting a turn: the lead's turns belong to the Router there.
- **Mid-turn input.** Each running turn has an inbox (`Running.inbox`). A user message for that bot, or its job's result, that arrives during the turn goes in, and the session's `PostToolUse` hook hands it to the model after its current tool call, fenced as `<new_input>`. It is the same hook that carries the wrap-up note and a subscribed Worker's thread events (`SessionConfig.midTurnNote` beside `SessionConfig.deliveries`; a session only ever has one of the two). At the end of the turn, if every message after its start was handed over that way, the bot's cursor moves past them and the turn queued for them is dropped (`settleMidTurn`); otherwise that turn runs as before. Messages with images are never injected.
- **Lifetime.** Jobs are stopped with the chat's Stop, "Start new topic" and when the chat is deleted; their writes are not reported as outside edits (`projectRunning` counts them); git operations on the chat's workspace wait for them. On shutdown they are killed but left "running" on disk, so the next start marks them stopped (`Crew restarted`) and posts their output without starting a turn. Records and logs are kept for 14 days, at most 200 per chat.
- **Seeing it**: a Background jobs bar above the composer (beside the Workers bar in a two-layer chat; title, bot, command, status, elapsed time, line count, Stop), a dialog with the full log page by page (and "Follow in terminal", which opens the Terminal tab on `tail -f` of the log) or a sub-task's transcript, and a compact result card in the chat. The Triggers view labels `job` results. API: `GET /api/jobs?chatId=`, `GET /api/jobs/:id/log?from=&lines=`, `POST /api/jobs/:id/stop`; `ServerEvent` `job`, `job_deleted`; `Bootstrap.jobs`.

## Chain of recall (Super-agent, Inline & Spill)

The fifth step (design: [ADR 005](docs/adr/005-chain-of-recall.md)): the context window is treated as a cache. Behind `superAgent.recall.enabled`, which only counts while `superAgent.enabled` is on; both are off by default. The one check is `recallBudget()` (`recall/index.ts`), read when a session starts: undefined means every prompt builder and tool list takes its old path.

- **Ids everywhere.** Every injected object carries its id: messages `#seq` (plus `answers #n` when a reply answers something other than the message just before it), Triggers `tg_…` and their Threads `th_…`, Workers `wk_…`, [background jobs](#full-duplex-background-jobs-super-agent) `job_…`, the [Watchdog](#watchdog-super-agent-external-control-loop)'s actions `wa_…` (a notice reaches a Router as an environment event under its action's id; a nudge tells the Worker its id), ticks `wt_…` and watches `ww_…`, the environment `env`, the conversation `chat`.
- **Budgets** (`recall/spill.ts`, pure). The focus of a turn (the latest message, the handoff) gets 300 words, the user's own words 600, what sits next to the focus (the message just before it, the one it answers) and a recalled object's body the setting `inlineWords` (50), everything else one line of 15 words. A text over its budget is cut at a word boundary and ends with `… (+N words: recall id=… from=M)`. Words are counted like the Router's reply limit (CJK characters count one each).
- **Where they apply.** `buildTurnPrompt` (group turns, direct chats, session recaps; the blind reviewer's prompt is unchanged), the Worker's prompt, and the Router's batch (user words, Worker reports to 50 words with `recall id=wk_…`, environment events with `recall id=tg_…`, and each user or routine event's Trigger id; the `<workers>` lines and the `<direct>` block of [direct routing](#thread-subscriptions-and-direct-routing-super-agent) already carry only ids and one line each). An event delivered straight to a subscribed Worker keeps its first ~60 words, and with recall on the cut names `recall id=tg_…`. `contextDelta` treats the environment as the object `env`: later turns say how many lines are unchanged and that `recall id=env` shows them. A background job's result is already inlined by its own rules (head and tail, `status` for the rest), so when it is the focus of a turn it is sent as it is rather than cut again at 300 words, which would lose the tail where a failure shows.
- **The tool** (`recall/graph.ts`). `recall(id, from?)` resolves an id inside the caller's scope (its chat; Triggers and Threads of its chat or project, a workspace counting as its parent; Workers of its chat) and renders it under the same budgets: a header with its facts, the start of its body, its neighbours (previous, next, the message it answers) and its links (a message's Triggers, Threads and the Workers it led to; a Trigger's thread, the message it records, related ids, the Workers it led to and the Workers it was delivered to directly, and who handed it back; a Thread's latest Triggers, the Workers on it and its subscribers; a Worker's chat thread, the batch it came from, the Thread of its own workspace and the Threads it subscribes to). With `from` it returns one 600-word page. Environment content (a non-explicit trigger's payload, a job's output) is in the `<untrusted>` wrapper, read-more handle included. A blind reviewer only recalls the user's messages and outside-edit notes, as `chat_history` showed it. Other kinds plug in with `registerRecall(prefix, resolver)`: background jobs, `job_…` (jobs of the caller's chat, and jobs whose result was delivered to one of its Workers; what it ran, its status and its output's head and tail, linked to the turn that started it, its result message and its Trigger; a message links to the jobs it started or reports), and the Watchdog (`watchdog/recall.ts`): `wa_…` (an action, its tick and its target), `wt_…` (a tick, with the flags about this chat and its actions here), `ww_…` (a watch) and `watchdog` (its state, open watches and recent actions concerning this chat), only what concerns the caller's chat. A Worker links to what the Watchdog did to it.
- **Folded in.** Chat and Worker sessions get `recall` in place of `chat_history` (the `crew` MCP server, beside a subscribed Worker's `unsubscribe_thread` and `hand_back`); the Router gets a read-only `recall` in `crew_router`, which changes nothing about what a batch may do (an environment-only batch still cannot dispatch). Toggling the setting restarts idle sessions (chats, Workers, Routers), since a session's tools are fixed when it starts; Claude Code keeps a resumed session's first system prompt, so the first turn of a resumed session says recall replaced `chat_history`. A Worker the Watchdog restarts starts a new session, which reads the setting afresh. The friction brief names `recall` instead of `chat_history` while it is on. The Watchdog keeps its own read-only `inspect` for the ids in its snapshot, since it sits outside every chat's scope.
- **Measuring.** Each chat, Worker and Router turn builds its prompt with and without the rules, logs both estimates (`recall` logger, about four characters per token) and keeps them as `meta.injected`. `tests/unit/recall-tokens.test.ts` does the same on a fixed fixture (`tests/fixtures/recallFixture.ts`) and pins the direction.
- **Seeing it**: `GET /api/recall/:id?chatId=&from=` returns what an agent in that chat would read (404 while off). Settings → Super-agent → Chain of recall has the switch and the inline budget.

## Watchdog (Super-agent, external control loop)

The sixth step (design: [ADR 006](docs/adr/006-watchdog.md)): a control loop outside the chats it watches. Behind `superAgent.watchdog.enabled`, which only counts while `superAgent.enabled` is on; both are off by default, and off means no timer, no `watchdog/` folder and no model call (`syncWatchdog` stops the timer when the settings change).

- **Timer and fast path.** A croner job (`*/N * * * *`, `superAgent.watchdog.everyMinutes`) calls `tick()`. Each tick first settles watches in code (`housekeepWatches`), then gathers a **snapshot** (`gatherSnapshot`): Workers that are active or ended since the last look, with their progress read off their log (`signals.ts`: the last tool call's time, the latest calls with repeats collapsed), approvals waiting for the user (`openApprovals()` in `permissionGate.ts`), turn errors and other friction since the last look (`readFriction`), Routers in error and preview console errors (from the trigger log), open watches, and, while the [audit log](#safety-lifecycle-skills-drafts-and-the-guard) is on, the command guard's refusals grouped per agent (Worker, background job, else bot in its chat) and rule, and failed runs of approved drafts (`auditSnaps`). Rules in code (`snapshot.ts`) flag a Worker as `stuck` (no progress for `stuckMinutes`), `looping` (the same call 4 times among its latest), `failed` or `failed-transient`; an approval waiting 10 minutes; any new turn error, friction, interface error; a due watch; an agent the guard refused at least twice (`guard:<agent>`: it keeps trying to get around a hard rule); a failed draft run. No flag, no model call: the tick is recorded as `quiet` or `healthy`. "Tick now" (`POST /api/watchdog/tick`) always looks, within the limits.
- **The session.** Like the Router's: one Claude Code session with no built-in tools (`tools: []`), its own system prompt (`prompts.ts`, with the same `<untrusted>` rule as every other prompt), no settings files, a `canUseTool` that refuses anything but `mcp__crew_watchdog__*` and, like every agent session, the deny hook (blocked actions, then the command guard; `watchdogSessionConfig`), working in `CREW_HOME/watchdog`, turns logged by `runLogged` under `watchdog` in `messages/`, one at a time through a `BatchQueue` (ticks coalesce). Its model and environment come from `botModel` and `agentEnv` with the `watchdog` scope, so with the [model gateway](#model-gateway-super-agent) on, its calls follow `gateway.roles.watchdog` and the spend windows for that role; a gateway change makes it start a new session at its next turn, never mid-turn (`invalidateWatchdog`). The snapshot follows Inline & Spill: ids everywhere, text cut to its first words, `inspect <id>` for the rest (Workers, triggers, ticks, watches, audit entries, jobs, chats); every outside text (task, tool calls, report, approval, error, console line, friction key, refused command) is in a one-line `<untrusted>` block, and the snapshot's own tags are defused inside it. A session past `rotateAtTokens` starts over with a recap of recent actions.
- **Tools and gates** (`tools.ts`, `gates.ts`): `nudge_worker` (a note queued with the Worker's follow-ups; `workerPrompt` renders it as the Watchdog's, which can only refocus, with its action id so the Worker can recall why), `stop_worker` (optionally with a `redirect` note it resumes with at once), `restart_worker` (`restartWorker` in `layers/workers.ts`: a failed or stopped Worker starts a new session from a recap of its task, last report and branch; it keeps its thread subscriptions, and once running it receives its threads' events again), `notify` (a Router gets an environment event, which cannot start or steer Workers; other chats a UI-only note), `watch`/`resolve_watch`, `propose_change` (maintainer turns only) and the free `inspect`. Every action, done or refused, is a line in `watchdog/actions.jsonl`. Hard limits from Settings: `maxTicksPerHour`, `maxActionsPerTick`, `dailyBudgetUsd` (ticks and questions together); constants cap nudges (2) and restarts (3) per Worker and notices (4) per chat per day.
- **Transient failures.** `isTransient` reads overloaded, rate limits, 429/5xx, timeouts and connection errors. A Worker failing that way gets a watch opened by code; a due watch flags the tick; checks back off from 5 minutes to at most 2 hours; code resolves the watch as soon as the Worker is running or done again, and gives up after 8 checks with a notice to the chat. (With the gateway's failover, most quota and outage errors are handed on to the next member before a Worker ever sees them; what still reaches it is what every member refused.)
- **Maintainers.** The Watchdog page has a chat: a message is a turn in the same session with the current snapshot attached. It can propose new trigger policies or a bot's role description (`watchdog/proposals.json`); accepting applies them through the settings store or `updateBot`, unless the value changed since (then the proposal is `stale`).
- **Seeing it**: the Watchdog page (sidebar, only while it is on) shows its state, next tick, ticks this hour, spend today and actions against the limits, pending proposals (Accept/Reject), open watches, recent actions and ticks, and the chat. API: `GET /api/watchdog`, `GET|POST /api/watchdog/messages`, `POST /api/watchdog/tick`, `POST /api/watchdog/proposals/:id/accept|reject`, `POST /api/watchdog/watches/:id/resolve`; `ServerEvent` `watchdog`.

## Speculative execution (Super-agent, silent reproduce-and-fix)

The eighth step (design: [ADR 008](docs/adr/008-speculative.md)): Crew acts ahead of the user on environment signals, spending background compute to save human waiting, and stays quiet unless the result is useful. Behind each project's own switch (`Project.speculative.enabled`, off by default), which only counts while `superAgent.enabled` is on; with it off, the Trigger listener returns at its first line, nothing is recorded and `CREW_HOME/speculative/` is never created. The shared limits are `superAgent.speculative`.

- **When** (`speculative/rules.ts`, pure, in `autoChallenge`'s style: rules read off facts, never a model's judgment). `onTrigger` in the bus hands every recorded Trigger to `speculative/index.ts`. Three signals, each a project switch: a full-duplex bot's background job that **failed** and is the project's check command or reads like a check (`failing-check`); preview console errors left after the fast path's noise rules (`console-error`); a user message that describes a problem and does not ask for the fix (`bug-report`: a request for the fix already went to a bot). Then gates, in order: the switches, a check command (the project's, else `npm test` when package.json has a real test script), not already delivered to subscribed Workers, a chat to surface in (the Trigger's, else the latest on the project) whose lead can work unattended (not a blind reviewer, level `edits`, `review` or `auto`, budget left), a git project, the same fingerprint not speculated on in 24 hours, fewer than `maxConcurrent` runs in flight and none in this project, and today's spend under `dailyBudgetUsd`. A matched signal a gate refused is recorded as `skipped` with the reason.
- **The run** is a Worker with `speculation: sp_…` (`layers/workers.ts`, through `SpeculativeHost`): same session, transcript (`wk_…`), gate, sandbox, deny hook, guard, stripped environment and budget as any Worker, but it starts in `createSpeculativeWorkspace` (a worktree of the observed state, the source folder's uncommitted tracked changes taken with `git stash create`, no chat lock and no move into a workspace), runs `unattended` (`permissionGate` refuses what would ask, with no card), has the check command pre-allowed, gets `speculative_result` instead of `notify_user`, `remember` and `draft_external_action`, is left out of the Workers bar, the Router's lines and limits, the Watchdog and `isChatBusy`, never subscribes, reports or lands, uses the gateway's `speculative` role (`superAgent.speculative.model`, else the Workers' model), and is stopped after `maxMinutes`. Its prompt (`speculative/prompts.ts`) wraps the signal's text in `<untrusted>`, states the protocol, and carries the project's triage, reproduce and draft-fix skills in `speculative` mode.
- **Verification** (`speculative/verify.ts`), in code: the run must claim it reproduced the problem and name its reproduction files; the rest of its change is the fix, which must exist and stay small (`maxFixLines`, 10 files). Then the check command must pass at the run's commit and fail with the fix files put back as they were in the observed state (reproduction kept). Checks run through `jobs/runner.ts` like a background command: sandboxed as a one-call helper session while the sandbox is on, else in a process group with the stripped environment; 10 minutes each.
- **Surfacing.** A verified fix is `ready`: a `speculative` Trigger on the chat's thread (fast path rule `speculative-ready`, its payload built from facts), a UI-only chat note (`notice: 'speculative'`), a toast, a Speculative fixes bar above the composer (summary, files, the exact diff, Merge, Discard), and in two-layer mode an environment event for the Router, which may mention it but cannot act on it. **Merge** applies the diff with `git apply` where the problem was seen (the chat's workspace, then committed; or the project folder, uncommitted), under the chat's lock as Crew's own writes, after `git apply --check`; a system note tells the bots which files changed. Everything else (not reproduced, no fix, too large, checks failing either way, stopped, out of time, restarted, not merged within a day) is `discarded` with the reason, its worktree and branch removed, and no chat hears of it.
- **Seeing it**: the card and bar in the chat, the Triggers view's `speculative` source, Settings → Super-agent → Speculative runs (limits, today's spend, recent runs and why each was skipped or discarded), and the project settings (switch, check command, signals, fix size). API: `GET /api/speculations?chatId=&projectId=`, `GET /api/speculations/:id`, `GET /api/speculations/:id/diff`, `POST /api/speculations/:id/merge`, `POST /api/speculations/:id/discard`; `ServerEvent` `speculation`; `Bootstrap.speculations`.

## Safety: lifecycle skills, drafts and the guard

The seventh step (design: [ADR 007](docs/adr/007-lifecycle-skills.md)) borrows Apache Magpie's model: external content is data; nothing leaves the machine in the user's name without a person's click; the agent is confined before it reads anything real; confirmations are budgeted; gates are deterministic; every agent-authored action is audited. The switches are `settings.safety` (`guard` and `stripCredentials` on by default, `audit` off) and, per project, `skillFamilies` and `passEnv`. None of it needs the Super-agent switch: the guard, drafts and stripping apply to chat turns as much as to Workers.

- **Lifecycle skill families** (`shared/families.ts`, `skills.ts`): a skill's front matter may declare `family` (triage, reproduce, draft-fix, review, release, repo-health), `modes` (`chat`, `worker`, `speculative`; default chat and worker) and `readOnly`. Skills without a family are general and behave as before. A project opts in per family; `skills.forPrompt(project)` lists general skills plus the enabled families in the system prompt of a bot, a Worker or a full-duplex sub-task, and `skills.forFamily(project, family, mode)` is how Workers (mode `worker`) and speculative runs (mode `speculative`: triage, reproduce and draft-fix) get a family's skills. Built-ins cover each family; review's adversarial skill hands the change to Skeptic, the reviewer `autoChallenge` uses.
- **Workers pick skills by family.** `dispatch_worker` takes `family` (beside `subscribe` when direct routing is on); code refuses one the chat's project has not enabled. The Worker's first prompt gets the family's worker-mode skills as a playbook (`playbookText`), and so does the first prompt of a Worker the Watchdog restarts, since the family is kept on the Worker. The Router's system prompt lists the enabled families with the chat's adversarial reviewer; changing a project's families restarts idle Routers. A Worker on a read-only family (triage, repo-health) is refused every file edit by its PreToolUse hook (so even acceptEdits cannot write), and a command that changes something asks whatever its level.
- **Reads never prompt; changes prompt once.** For every shell command it lets through, the guard says whether it only reads (a known reader such as `cat`, `rg`, `find` without `-exec`, `git status|log|diff|show…`, without redirection or substitution) or changes something, with a summary ("Deletes: dist", "Installs packages: npm install", "Writes file: out.txt", "Connects to: registry.npmjs.org"). `permissionGate` passes the read verdict to `decide`, which then allows at any level (after the must-ask rules); a change's approval card lists the summary above the raw command, and a command the user allowed earlier in the turn is not asked again. A full-duplex bot's `start` asks the same gate, so a background command gets the same verdict and card.
- **Draft-only external actions** (`drafts.ts`, the crew MCP tool `draft_external_action`, offered to bots, Workers and sub-tasks): a push, a pull request, an issue, a comment or a message is drafted by the agent. Crew builds the exact argv from validated fields (a branch or remote that could be read as an option or a revision expression is refused) and stores the draft in `drafts.json`; nothing runs. The Drafts bar above the composer (below the Workers and Background jobs bars) and Settings → Safety show the kind, the target, the exact command and the text, with "Approve and run" and "Discard". Approving runs the argv with `execFile` in the folder it was drafted in (a Worker's draft: its worktree), with the user's own environment, records the output and the URL it printed, and works out how to reverse it (for a push, Crew reads the remote's old head with `git ls-remote` first). A system note tells the chat. There is no setting that runs a draft without the click.
- **Credential-stripped environment** (`config.cleanEnv`, `safety.agentEnvOptions`, applied by `agentEnv(scope, model, project)`): every agent session (bots, Workers, Routers, the Watchdog, sub-tasks and the sandboxed helpers of background jobs) gets Crew's environment without variables that look like secrets (`*TOKEN*`, `*SECRET*`, `*API_KEY*`, `AWS_*` keys, `SSH_AUTH_SOCK`…), and so does a background command Crew runs itself. The model's own connection is added after stripping: Anthropic's variables, the Claude Code ones Crew keeps, a cloud's credentials when Claude Code runs on that cloud, or, with the [model gateway](#model-gateway-super-agent) on, only the session's own scope token. `Project.passEnv` passes named variables through. The user's terminal, setup commands and approved drafts keep the full environment. Turning stripping on or off restarts idle sessions, Routers and the Watchdog.
- **External content is data** (`untrusted.ts`): page text and HTML in a picked element, captured console output and recorded steps in a user's message, `preview_console` and `browser_act` results, the Router's environment events (with or without the chain of recall), events delivered straight to a subscribed Worker, the slow path's events, background job output (results, `stop`, `status`), recalled environment objects, and every outside text in the Watchdog's snapshot and `inspect` results are wrapped in `<untrusted source="…">` blocks that cannot be closed from inside; a PostToolUse hook labels WebFetch and WebSearch results (beside the hook that carries the wrap-up note, mid-turn input and thread deliveries). Every system prompt (bots, Workers, the Router, the slow path, the Watchdog) says what the blocks mean, and that material the user pasted is data too.
- **Audit log** (`audit.ts`, `audit.jsonl`, opt-in): one JSON line per drafted action, approval, discard, run (exit code, output, reverse command) or failure, and per guard refusal (rule and command, including a refused background command), each naming the bot, chat, Worker or background sub-task (`actor.jobId`). The [Watchdog](#watchdog-super-agent-external-control-loop) reads its refusals and failed runs. At most 5,000 entries / 180 days. Settings → Safety shows it live (`ServerEvent` `audit`) next to every draft and a box that shows the guard's verdict on a command (`POST /api/guard/check`).
- API: `GET /api/drafts`, `POST /api/drafts` (a draft made by hand), `POST /api/drafts/:id/approve`, `POST /api/drafts/:id/discard`, `GET /api/audit`, `POST /api/guard/check`; `PATCH /api/settings` accepts `safety`, `PATCH /api/projects/:id` `skillFamilies` and `passEnv`; `ServerEvent` `draft` and `audit`; `drafts` in `Bootstrap`.

## Hardening against untrusted input

ADR 007 labels outside text and adds deterministic gates; [ADR 104](docs/adr/104-injection-hardening.md) assumes the labels sometimes fail and the model does whatever an injected payload says, then closes every hole that showed up when we red-teamed that case (`tests/integration/injection.test.ts`: the real Claude Code, a mock model scripted to obey payloads from a chat paste, an outside edit, a routine's output, a console error, a job's output and a recalled object, with the bot in Full auto). The code is in `server/hardening/`, hooked into the existing modules with a few lines each; there is no new setting.

- **The agent fence** (`fence.ts`, mounted on `/api` and the `/ws` upgrade in `index.ts`). Loopback requests are trusted as the user's, and every agent command runs on this machine, so without it a command could change settings, approve its own draft or open the user's terminal. On Linux, the TCP peer of each new connection is looked up in `/proc/net/tcp{,6}` and the file descriptors of the server's descendants; a request from one of them (Claude Code sessions and, through the sandbox, their proxy, commands, MCP servers, jobs, dev servers, Crew's headless Chrome) gets 403, a log line and an audit entry (`crew-api`). The user's terminals are registered as trusted (`terminal.ts`). Cached per socket; a few milliseconds per new local connection.
- **The key broker** (`broker.ts`, used by `claudeAuth.modelEnv` for every scoped session). While `safety.stripCredentials` is on and the gateway is off, a connection whose key is in `settings.json` is reached through a loopback listener: sessions get its address and a per-process token, and it forwards each request unchanged with the real key. With the gateway on, the gateway's scope tokens do the same (ADR 009). Started with the server and re-synced when the connection or safety settings change; connection tests and `claude auth status` still use the key directly.
- **The guard, hardened** (`commands.ts`, `paths.ts`, called per simple command from `guard.ts`). A single `&` separates commands; `cd` moves the folder later segments are resolved in; computed command names and scripts piped into a shell or an interpreter are refused (`opaque`); program-valued variables (`GIT_SSH_COMMAND`, `EDITOR`…) and `git -c` settings are judged as commands; credential stores are refused when reached by glob, through a folder a recursive reader is given, or under `/proc/<pid>/environ|cmdline|mem`; writes to `.git` hooks and config, `.claude/`, `.mcp.json`, `.vscode/`, `.idea/`, Crew's data folder (except worktrees) and the home folder's start-up files are refused (`config`), and so are `git config` writes to program-valued or redirecting keys, `git remote set-url` and `crontab`; network tools to Crew's own port and WebFetch to it are refused (`crew-api`); deploy and cloud CLIs, `git subtree push` and friends are `external`. Settings → Safety labels the new rules.
- **The sandbox, given the same paths** (`sandboxPolicy.ts`, merged by `sandboxOptions(…, cwd)`): `filesystem.denyRead` for the credential stores and `settings.json`, `filesystem.denyWrite` for the session folder's and its repository's hooks and config, the tool settings folders, Crew's data and the start-up files, and `credentials.envVars` unsetting the model variables for commands.
- **Agent-written code without credentials**: the dev server (`devserver.ts`) and workspace setup commands (`workspaces/setup.ts`, also for Workers' worktrees) get the stripped environment with the project's `passEnv`.
- **Drafts run what the card shows** (`draftChecks.ts`, used by `drafts.ts`): a push records its resolved push URL (shown on the card) and refuses to run if it changed; a git or gh draft is not run when the repository's own config runs a program or redirects remotes; drafts run with `core.hooksPath` set to `/dev/null` through `GIT_CONFIG_*`, so the argv is unchanged.
- **Outside edits are data** (`outsideEdits.ts`): the list of files and changed lines is wrapped in `<untrusted source="outside-edit">` (the UI shows it without the tags), and files that usually hold secrets (`.env*`, keys, credential JSON…) are named but never quoted.
- **Redaction at every sink** (`secrets.ts`, `redactor.ts`): every secret in `settings.json` (keys, provider and gateway tokens, plugin secrets, the LAN token, the Bark key) and the broker's token are replaced with `[redacted]` in the server log, the audit log, Trigger summaries and payloads, stored messages, job logs and draft output, and in every API answer and WebSocket event (the LAN token excepted there: the phone-access link shows it).

What is left (a script the agent writes and runs is opaque to the guard; plugin secrets on Claude Code's command line; the fence on macOS; memory notes; injection relayed through Worker reports within the hop limit) is listed with the reasons in the ADR.

## Model gateway (Super-agent)

The ninth step (design: [ADR 009](docs/adr/009-model-routing.md)) lets every agent use any model, with failover between providers and accounts. It sits behind `gateway.enabled`, off by default, and is independent of `superAgent.enabled`; off, `modelEnv()` and `botModel()` return what they always did, nothing listens and no file is created.

- **Where it sits.** `gateway/index.ts` runs an HTTP server on `127.0.0.1` (`gateway.port`, 0 = any free port), started in `index.ts` before anything can start a session and re-synced when the settings change. Every Claude Code session Crew starts gets `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>/s/<role>/<botId>` and `ANTHROPIC_AUTH_TOKEN=<scope credential>` (an HMAC of the scope with a per-process secret), from `modelEnv(settings, scope)`: chat turns pass `bot` (so do a full-duplex bot's sub-tasks and sandboxed job helpers, which are its own spend), Workers `worker`, the Router `router`, the Watchdog `watchdog`, `oneShot` `oneshot`, speculative runs `speculative`. The gateway refuses a credential that does not match its path, so an agent cannot spend under another role's window, and provider keys (`gatewayTokens` in `settings.json`) never reach an agent's environment.
- **Routing** (`gateway/config.ts`, pure). A target is a group (an ordered list of `provider/model` members) or a `provider/model`. `routeFor(scope, model)`: the gateway's role override (`gateway.roles`), else the model asked for when it is an address (this is how each bot picks, through its own model field and the chat's switch, how the two layers pick, through `superAgent.router.model` and `workerModel`, and how the Watchdog picks, through `superAgent.watchdog.model`), else `defaultTarget`. So the two-layer split is two settings: the Router (and the Watchdog) on a light group, Workers on the strongest one. The session's model and its tier variables are set to the target; Claude Code's haiku tier goes to `fastTarget` when set. A `provider/*` member passes the requested model through.
- **Failover** (`gateway/proxy.ts`). Members are asked in order; no connection, 429, 5xx, a 400/402/403 that says quota/balance/billing, or a stream whose first event is an overloaded/rate-limit/api error hands on to the next member. Nothing reaches the client until a member answered, and a stream's first event is held back until it is known not to be such an error, so failover is transparent for streams too. Other errors are final. When all refuse, the last refusal goes back (status, body, `retry-after`). Upstream requests go through `gateway/upstream.ts`, which honours `HTTPS_PROXY`/`NO_PROXY` (Node's http does not).
- **Spend windows** (`gateway/windows.ts`, pure): rolling per role (and optionally per bot) limits in USD and tokens, checked against the usage log before any provider is asked; a spent window answers 429 with `Retry-After` and `x-should-retry: false`, and the call is logged as `limited`.
- **Usage log**: one `GatewayCall` per call in `gateway/calls.jsonl` (`JsonlLog`, 20,000 / 35 days): scope, requested model, target, the provider and model that answered, every try, tokens (from the response's usage, `message_start` + `message_delta` for streams), estimated cost (`gateway/pricing.ts`: the provider's price, else Anthropic's list prices), latency. `GET /api/gateway` returns it with totals and window states; `POST /api/gateway/test` sends a tiny prompt through the real listener.
- **Masking** (`gateway/mask.ts`, pure, off by default): emails, common key shapes and assigned passwords in `system`, text, tool results and tool inputs become `CREW_MASKED_<KIND>_<hmac>` (stable per value, so resent history stays cacheable); replies are restored, streams per content block with a restorer that holds back a possible partial placeholder. Thinking blocks are never changed, so their signatures stay valid.

## Adversarial review

Builders (Pixel and others), acceptance (Probe) and review (Lens) all look for supporting evidence, and each one sees the previous one's conclusion, so they tend to vouch for each other. Skeptic is the link dedicated to finding counter-evidence. Its design has these points (`server/review.ts`, `blindPrompt`):

- **Isolation** (both Skeptic and Lens): each turn a `blindReview` agent receives only the user's messages and the diff of the changes (all changes relative to the base in an isolated workspace; for a plain project, the uncommitted changes, or the last commit if there are none). It is told only how many messages teammates sent, and `chat_history` returns only the user's messages. Combined with a fresh session every turn, the author's reasoning cannot influence it.
- **Evidence only**: only a reproducible counterexample counts as a refutation; reasoning and guesses are recorded as "could not verify". Precision comes first.
- **Read-only**: it may only write `tests/challenge/**`; fixes go back to the author.
- **Can trigger automatically**: when a project has `autoChallenge` on, after a chain of turns ends and the chat is idle, fixed rules (which files changed, how many lines) decide whether to ask Skeptic; at most twice per request, and the same state is never reviewed twice (`server/autoChallenge.ts`).
- **Can act as a gate**: its verdict (the closing `Verdict: not refuted` or `Verdict: refuted N` line) is recorded on the isolated workspace, together with the commit it saw. When a project has `requireChallenge` on, merging requires a verdict for the current commit that refuted nothing.

The model follows the default (Opus 5.5). In the research, "models cannot fix their own mistakes" mostly comes from the author's reasoning staying in context, and isolation already cuts that off; changes Chief writes itself use the same model as Skeptic, so blind spots may overlap. This is a known trade-off.

## Group chat routing (shadow mode)

In a group chat, every message without an @ goes to the lead first (usually the most expensive model), even if it is just a small change. Following JEV-as-a-Judge (Li et al., 2026), `server/router.ts` prepares a cheap first pass that "accepts when confident, escalates when not", but for now it only records and does not act:

- **Cheap judgments are used only where the answer can be read off the text**: "who should take this" can be judged from the request itself; "is the code correct" requires reasoning, and in the paper cheap judges lose 7-28 points on that kind of question, so the router never judges code.
- **Average over two orders**: list the candidates once forwards and once backwards, align, and average the probabilities to cancel the position bias of "preferring the first one".
- **Labels come from real outcomes**: if the lead did the work itself, the label is the lead; if it handed off to one teammate, that teammate; if it handed off to several, the record does not count.
- **The threshold is chosen from local labels using a lower bound**: once 100 records with outcomes have accumulated, choose the smallest threshold such that the 95% lower bound (Wilson) of the accuracy of decisions above it is at least 90%. The paper shows that choosing the threshold by the lower bound rather than the point estimate cuts the risk of "dropping more than two points" from about 45% to about 5%.
- One-shot calls are all "bare": no tools, no Claude Code system prompt, no settings or MCP loaded.

## Improvement suggestions (lightweight self-improvement)

Full self-improvement needs an evaluation suite to judge whether a change is better; without one it manufactures "fake progress". Crew does not change itself automatically; instead it uses the human as the evaluation (`server/improve.ts`):

1. **Evidence pack**: the team's current settings, the last 60 turns (cost, model, status, approvals and their reasons, failing tools, refutation verdicts), the original text of refuted turns, the user's recent words, and earlier suggestions and decisions (the ledger).
2. **Proposal**: one `claude -p` call (Sonnet) returns JSON suggestions. The constraints follow the RRSI approach: at most 3 per run, each one field of one agent, a role description changes by at most 8 lines at a time, real turns must be cited, and proposing nothing is better than proposing badly.
3. **Checks**: the agent exists, the new value passes `BotPatch` validation, it differs from the current value, the evidence really exists, the evidence comes from at least two different user requests (added because on the first real run all three suggestions came from the same incident), and it does not duplicate a pending or rejected one. Suggestions that fail are dropped with the reason stated.
4. **Decision**: the user can edit first (the new value goes through the same `BotPatch` validation, and the model's original value is stored as `original`), then accept (applied to the agent; if the setting was changed by hand after the proposal, the suggestion is void), reject (optionally with a reason) or withdraw. Rejection reasons and "what the model proposed -> what the user changed it to" both go into the ledger for the next analysis.
5. **Effect**: after accepting, compare the average cost, refutation count and error count over the same number of turns before and after the change. This is only an observation, not a controlled experiment; different tasks introduce bias.

The ledger is stored in `~/.crew/improvements.json`.

## Learning from experience

Borrows the learning loop of Hermes Agent, but every step needs human approval (the paper Practice Makes Unsafe found that systems which automatically write skills from successful experience and apply them automatically all ended up writing unsafe skills):

- **Memory nudge**: when a turn makes 5 or more tool calls, the next turn's prompt in the same session ends with a reminder (`MEMORY_NUDGE`) to record only what the user said and what was verified first-hand. No reminder after switching to a new session or for blind-review roles.
- **Learned skills** (`server/learnSkills.ts`): candidates are turns that completed, made 5 or more tool calls, were not refuted afterwards and have not been drafted yet; listing them is free, drafting takes a click and one Sonnet call. A draft first goes through fixed safety checks (blocked rules and "ignore instructions"-style text are rejected outright; commands that need confirmation and addresses outside the sandbox are flagged), then shows up as a "new skill" suggestion in the improvement suggestions panel. It is written to the skills directory only when accepted, and deleted when withdrawn.

- All writes in `store.ts` are "write a temp file, then rename", and are batched and deferred; on exit `flushAll()` finishes any pending writes.

## Isolated workspaces

A chat can work in its own git worktree, on a branch starting with `crew/`; agents, preview, files and terminal all use that copy.

- On creation it brings along local files that git does not track but that the work needs: `.env`, `CLAUDE.md`, settings and hooks in `.claude/`, and files listed in `.git/info/exclude`. Dependency directories, caches and tools' temporary state are not copied. Only files that `git check-ignore` confirms are ignored inside the worktree are copied, so `git status` stays clean.
- A project can configure a setup command, commit message requirements, no AI attribution, and actions that always need confirmation.
- Merging squashes the branch into one commit on the main branch. When the project has commit message requirements, the commit message must be written by hand (`claude -p` can generate a draft).

## Preview

`preview.ts` starts one preview server per project: static sites are served directly (hidden files are not served), and projects with a dev server are reverse-proxied to it. Returned HTML gets `inject/preview-inject.js` injected; it talks to the Crew window via postMessage and handles console capture, navigation tracking, element picking, demo recording and hot refresh. This script runs inside someone else's page, so it is deliberately written in a conservative `function` + `var` style (the lint rules are relaxed for it specifically).

## Desktop app

`desktop/main.cjs` is the Electron main process: it starts the bundled server (`dist-server/server.mjs`) with the login shell's environment variables, waits until it is ready, and loads the UI in a window; the tray, launch at login, and Dock and window icons (following the logo chosen in settings) also live here. `desktop/install.mjs` packages the AppImage, installs it into `~/Applications`, and writes the menu entry and icon.

## A few design decisions

- **Use the local `claude`, not the SDK's bundled binary**: saves 240 MB, and the version follows the user's own Claude Code upgrades.
- **Biome rather than ESLint**: the project uses TypeScript 7 (the native version), which has no JS API, so typescript-eslint cannot run.
- **Routing uses the address bar hash (`#/chat/<id>`)**: each chat gets its own history entry, the browser's back and forward switch between chats, and a link can open a specific chat directly.
- **Tests use the system Chrome**: Playwright does not download browsers; CI uses the Chrome that comes with the runner.
